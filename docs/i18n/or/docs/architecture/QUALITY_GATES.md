ଏହି ଡକ୍ୟୁମେଣ୍ଟଟି OmniRoute ର ସମସ୍ତ CI ଗୁଣବତ୍ତା ଗେଟ୍ ପାଇଁ ପ୍ରାମାଣିକ ସନ୍ଦର୍ଭ।
ଏହା ପ୍ରତ୍ୟେକ ଗେଟ୍, ଏହା କ’ଣ ଯାଞ୍ଚ କରେ, କେଉଁ CI ଜବ୍ରେ ଏହା ଚାଲେ, ଏହା
ଏକ ରାଚେଟ୍ ବେସ୍ଲାଇନ୍ କିମ୍ବା ଏକ ପାସ୍/ଫେଲ୍ ନୀତି ବ୍ୟବହାର କରେ କି ନାହିଁ, ଏବଂ ଏହା ବିଲ୍ଡ୍କୁ ଅବରୋଧ କରେ କିମ୍ବା କେବଳ ପରାମର୍ଶମୂଳକ—ତାହା ବର୍ଣ୍ଣନା କରେ।

ଏକ ସଂକ୍ଷିପ୍ତ ସାରାଂଶ ଏବଂ ଅନୁମତି-ତାଲିକା ନୀତି ପାଇଁ, `AGENTS.md` ରେ ଥିବା
"ଗୁଣବତ୍ତା ଗେଟ୍ ଏବଂ ରାଚେଟ୍" ବିଭାଗ ଦେଖନ୍ତୁ। ସେହି ସିଷ୍ଟମ୍ର ସମାଲୋଚନାମୂଳକ ମୂଲ୍ୟାଙ୍କନ,
ପରିପକ୍ୱତା ବର୍ଗୀକରଣ ଏବଂ ଟୁଲ୍-ନିରପେକ୍ଷ ପ୍ରତିରୂପଣ ଯୋଜନା ପାଇଁ,
[ଗୁଣବତ୍ତା ଗେଟ୍ ପ୍ଲେବୁକ୍](../ops/QUALITY_GATE_PLAYBOOK.md) ଦେଖନ୍ତୁ।

## ଗେଟ୍ ଭଣ୍ଡାର ଏବଂ ଏକଜେକ୍ୟୁଟ୍ ପ୍ରୋଫାଇଲ୍ \|

### ପ୍ରାର୍ଥୀ ଆଡମିଶନ \|

CI ଏବଂ କ୍ୱାଲିଟି ଗେଟ୍ସ ୱାର୍କଫ୍ଲୋ ପ୍ରତ୍ୟେକ ଏକ ସ୍ଥିର ରାୟ ନିର୍ଗତ କରେ: `Gate / CI` ଏବଂ `Gate / Quality`\| ସେମାନଙ୍କର ସଂସ୍କରଣ ଆଡମିଶନ ନୀତି ପ୍ରତ୍ୟେକ ଅପଷ୍ଟ୍ରିମ କାର୍ଯ୍ୟକୁ ଆବଶ୍ୟକ କିମ୍ବା ପରାମର୍ଶଦାତା ଭାବରେ ଗଣନା କରେ \| ଏକ ପ୍ରଯୁଜ୍ୟ ଆବଶ୍ୟକୀୟ କାର୍ଯ୍ୟ ନିଶ୍ଚିତ ଭାବରେ ସଫଳ ହେବ: ନିଖୋଜ, ବାତିଲ୍, ଛାଡି, ବିଚାରାଧୀନ ଏବଂ ଅଜ୍ଞାତ ଫଳାଫଳ PASS ପ୍ରତିଷ୍ଠା କରିପାରିବ ନାହିଁ \| ଏକ ବ valid ଧ ଡକସ୍-କେବଳ କିମ୍ବା କାଟାଲଗ୍-କେବଳ ବର୍ଗୀକରଣ ଏକ କୋଡ୍ ଗାଡ଼ି ଅନୁପଯୁକ୍ତ କରିପାରେ \| ଏକ ଡ୍ରାଫ୍ଟ PR ଏକ ଗ୍ରହଣୀୟ ପ୍ରାର୍ଥୀ ନୁହେଁ \| ଏକ `hotfix` ଲେବଲ୍ ପ୍ରମାଣ ଛାଡ କରେ ନାହିଁ \|

ଉଭୟ ୱାର୍କଫ୍ଲୋ PRs main/release ଶାଖାରେ ଆବୃତ କରେ, `main` କୁ ଠେଲିଥାଏ, ମାନୁଆଲ୍ ପଠାଇବା ଏବଂ ମିଶ୍ରଣ-ଗୋଷ୍ଠୀ ଇଭେଣ୍ଟଗୁଡିକ \| ପୁସ୍, ପଠାଇବା ଏବଂ ମିଶ୍ରଣ-ଗୋଷ୍ଠୀ ପୂର୍ଣ୍ଣ ଚୟନ ଚଲାନ୍ତୁ \| `release/**` କୁ ଠେଲିବା ସେଗୁଡିକ ଆରମ୍ଭ କରେ ନାହିଁ (2026-10-18): ପ୍ରତ୍ୟେକ ପରିବର୍ତ୍ତନ ଏହାର PR ରେ ମ୍ୟାଟ୍ରିକ୍ସ ଚଲାଇସାରିଛି ଏବଂ ମିଶ୍ରିତ ମିଶ୍ରଣ ହେଉଛି ରିଲିଜ୍-ଗ୍ରୀନ୍ ର କାର୍ଯ୍ୟ (`docs/ops/RUNNER_BOX.md` → ହୋଷ୍ଟେଡ୍ ଲେନ୍) \| ଫର୍କସ୍ ଏବଂ ମିଶ୍ରଣ ଗୋଷ୍ଠୀଗୁଡିକ ଚାକିରି ପାଇଁ ହୋଷ୍ଟ ରନର୍ସ ବ୍ୟବହାର କରନ୍ତି ଯାହା ଅନ୍ୟଥା ସ୍ୱ-ହୋଷ୍ଟ ରନର୍ସ ଚୟନ କରେ \| ଯଥେଷ୍ଟ ହୋଷ୍ଟ କ୍ଷମତା ରୋଲଆଉଟ୍ ପୂର୍ବରୁ ଯାଞ୍ଚ ହେବା ଜରୁରୀ \|

ପ୍ରତ୍ୟେକ JSON ରସିଦ ଯାଞ୍ଚ ହୋଇଥିବା SHA, ୱାର୍କଫ୍ଲୋ ଚଲାଇବା ଏବଂ ପ୍ରୟାସକୁ ଚିହ୍ନଟ କରେ \| CLI ଏକ checkout/event SHA ଅସଙ୍ଗତିକୁ ପ୍ରତ୍ୟାଖ୍ୟାନ କରେ \| ୱାର୍କଫ୍ଲୋ ପରୀକ୍ଷଣ ନୀତି ସଦସ୍ୟତାକୁ ବିଚାରର `needs` ତାଲିକାରେ ବାନ୍ଧେ ତେଣୁ ଏକ ନୂତନ କିମ୍ବା ଅପସାରିତ ଗାଡ଼ି ଚୁପଚାପ୍ ଅଦୃଶ୍ୟ ହୋଇପାରିବ ନାହିଁ \| ରସିଦଗୁଡିକ ସେମାନଙ୍କର ନିଜସ୍ୱ କାର୍ଯ୍ୟ ପ୍ରବାହକୁ ଆବୃତ୍ତି କରେ, ପ୍ରକାଶନ, ନିୟୋଜନ କିମ୍ବା ଏକ ବିଦ୍ୟମାନ ପରାମର୍ଶଦାତା ସ୍କାନରର ଆଭ୍ୟନ୍ତରୀଣ ନୁହେଁ \| ଶାଖା ନିୟମରେ ଉଭୟ ଚେକ୍ ନାମକୁ ସକ୍ରିୟ କରିବା ଏକ ପୃଥକ ପ୍ରଶାସନିକ ପରିବର୍ତ୍ତନ; ଏହି ଚାକିରିଗୁଡିକ ଯୋଡିବା ନିଜେ ଏକ ଶାଖା ରକ୍ଷା କରେ ନାହିଁ \|

### ଷ୍ଟାଟିକ୍ ସ୍କାନ୍ ଭଣ୍ଡାର \|

ସଂସ୍କରଣ npm-alias inventary ଏବଂ static-scan ସଦସ୍ୟତା `config/quality/gate-manifest.json` ରେ ରୁହନ୍ତି \| ସ୍କ୍ରିପ୍ଟ ନାମ ଏବଂ `package.json` ବିରୁଦ୍ଧରେ ସଠିକ୍ ନିର୍ଦ୍ଦେଶକୁ ବ valid ଧ କରିବାକୁ `npm run check:gate-manifest` ଚଲାନ୍ତୁ; ଯୋଗ, ଅପସାରଣ ଏବଂ ନିର୍ଦ୍ଦେଶ ଡ୍ରାଇଫ୍ ଉଭୟ ସ୍ଥାନୀୟ ହୁକ୍ ଏବଂ CI ରେ ପରିବର୍ତ୍ତନ-ବର୍ଗୀକରଣ କାର୍ଯ୍ୟ ବିଫଳ ହୁଏ \| ଏକ ଛଦ୍ମନାମ ଏକ କାର୍ଯ୍ୟଧାରା କାର୍ଯ୍ୟ ନୁହେଁ, ମ୍ୟାଟ୍ରିକ୍ସ ଉଦାହରଣ କିମ୍ବା ପରୀକ୍ଷଣ ମାମଲା: ଏହି ଗଣନାଗୁଡ଼ିକ ଅଦଳବଦଳ ଭାବରେ ଉପସ୍ଥାପିତ ହେବା ଉଚିତ ନୁହେଁ \|

ସେଗୁଡ଼ିକୁ କାର୍ଯ୍ୟକାରୀ ନକରି ମନୋନୀତ ଛଦ୍ମନାମ ଯାଞ୍ଚ କରିବାକୁ `npm run quality:scan -- --list` କିମ୍ବା `npm run quality:scan:fast -- --list` ବ୍ୟବହାର କରନ୍ତୁ \| ରନର୍ npm ଏଣ୍ଟ୍ରିପଏଣ୍ଟକୁ ଆହ୍ .ାନ କରେ, ତେଣୁ ଏହାର ଚାଲିବା ସମୟ ( Bun ଅନ୍ତର୍ଭୂକ୍ତ କରି ଯେଉଁଠାରେ ବିନ୍ୟାସିତ) ସଂରକ୍ଷିତ \| ସେହି ପ୍ରୋଫାଇଲଗୁଡିକ ବାହାରେ ମନିଫେଷ୍ଟ୍ ରେକର୍ଡ ଛଦ୍ମନାମଗୁଡିକ ପୃଥକ ଭାବରେ ଆହ୍ as ାନ କରାଯାଏ, ଏବଂ ରକ୍ଷଣାବେକ୍ଷଣ ନିର୍ଦ୍ଦେଶଗୁଡ଼ିକ କେବଳ ପଠନୀୟ ସ୍କାନ ପ୍ରୋଫାଇଲରେ ନିଷେଧ \|

ଏହି ପ୍ରୋଫାଇଲଗୁଡ଼ିକ କେବଳ ଷ୍ଟାଟିକ୍ ସ୍କାନ୍ କୁ ଆବୃତ କରେ \| ସେମାନେ ଉତ୍ପାଦ ପରୀକ୍ଷା, କଭରେଜ, ପ୍ୟାକେଜିଂ, ବାହ୍ୟ ଯା s ୍ଚ କିମ୍ବା ଜଣେ ପ୍ରାର୍ଥୀଙ୍କ ପୂର୍ଣ୍ଣ ପ୍ରକାଶନ ଗ୍ରହଣକୁ ପ୍ରମାଣ କରନ୍ତି ନାହିଁ \| ୱାର୍କଫ୍ଲୋ ଆଡମିଶନ ସଂଯୁକ୍ତ `config/quality/admission-policy.json` ଏବଂ `scripts/quality/admission-verdict.mjs` ବ୍ୟବହାର କରେ \| ରିଲିଜ୍-ପର୍ଯ୍ୟବେକ୍ଷକ ପ୍ରୋଫାଇଲ୍ ଅଲଗା ରହିଥାଏ; ନିରପେକ୍ଷ ଭାବରେ ସେମାନଙ୍କର ପ୍ରଯୁଜ୍ୟ ଯାଞ୍ଚ ଏବଂ ରସିଦ ଯାଞ୍ଚ କରନ୍ତୁ \| ନିମ୍ନରେ ଥିବା ଗଦ୍ୟ ତାଲିକା ହେଉଛି ଏକ ରେଫରେନ୍ସ, ଏକ ଗେଟ୍ ପ୍ରକୃତରେ ଚାଲିଥିବାର ପ୍ରମାଣ ନୁହେଁ \|

#### ଭୁଲିଯାଇଥିବା ଭାଇଭଉଣୀ ପରୀକ୍ଷା ରିପୋର୍ଟ \|

ବ୍ୟାରେଲ୍ ପୁନ - ରପ୍ତାନି ଏବଂ ଗତିଶୀଳ ଆମଦାନୀ କେବଳ ରେଜୋଲୁସନ ଡାଇଗ୍ନୋଷ୍ଟିକ୍ ଅଟେ; ସେମାନେ କଦାପି ଏକ ଅବରୋଧକାରୀ ସନ୍ଧାନ ସୃଷ୍ଟି କରନ୍ତି ନାହିଁ \| ସମୀକ୍ଷା ହୋଇଥିବା ବ୍ୟତିକ୍ରମଗୁଡ଼ିକ `config/quality/forgotten-sibling-allowlist.json` ରେ ରୁହନ୍ତି \| ପ୍ରତ୍ୟେକ ଏଣ୍ଟ୍ରି ନିଶ୍ଚିତ ଭାବରେ ଗ୍ରାହକ ଏବଂ ପ୍ରାର୍ଥୀ ପରୀକ୍ଷଣର ନାମ ଦେବା, ଏକ ନିର୍ଦ୍ଦିଷ୍ଟ ଯୁକ୍ତିଯୁକ୍ତତା ପ୍ରଦାନ କରିବା, ଏବଂ ଏକ GitHub ଇସୁ ଲିଙ୍କ୍ କରିବା କିମ୍ବା ଅନୁରୋଧ ଟାଣିବା \| ବିକୃତ ଏଣ୍ଟ୍ରିଗୁଡିକ ବନ୍ଦ ହୋଇଗଲା \| ବ୍ୟତିକ୍ରମଗୁଡିକ ଏକ ବିଲୋପିତ ପ୍ରାର୍ଥୀ ପରୀକ୍ଷା କିମ୍ବା `.skip`/`.todo` ଯୋଗ କରୁଥିବା ଏକ ଭିନ୍ନତାକୁ ଦମନ କରିପାରିବ ନାହିଁ \| ଧାରଣା ଦୁର୍ବଳ ହେବା ଏବଂ ଅନ୍ୟାନ୍ୟ ମାସ୍କିଂ ସ୍ z ାଧୀନ ଭାବରେ `check:test-masking` ଗେଟକୁ ଅବରୋଧ କରିଥାଏ \|

## ଅନୁମୋଦିତ-ତାଲିକା ନୀତି

ପୂର୍ବରୁ ଥିବା ଉଲ୍ଲଂଘନ ଯୋଗୁଁ ବିଫଳ ହୋଇପାରୁ ନଥିବା ପ୍ରତ୍ୟେକ ଗେଟ୍ ଏକ ଅପରିବର୍ତ୍ତନୀୟ ଅନୁମୋଦିତ-ତାଲିକା ବ୍ୟବହାର କରେ
(ଯଥା, `KNOWN_STALE_DOC_REFS`, `KNOWN_MISSING`, `KNOWN_RAW_SQL`)। ନୀତିଟି ହେଉଛି:

**ମୂଳ କାରଣଟି ସମାଧାନ କରନ୍ତୁ; ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲେ ଏବଂ ସେହି PRରେ
ସମାଧାନ କରାଯାଇପାରୁ ନଥିଲେ ମାତ୍ର ଅନୁମୋଦିତ-ତାଲିକା ବ୍ୟବହାର କରନ୍ତୁ।**

ଏକ ଅନୁମୋଦିତ-ତାଲିକାରେ ଏଣ୍ଟ୍ରି ଯୋଡ଼ିବାବେଳେ:

1. ଯଥାର୍ଥତାର କାରଣ ସହିତ ଏକ ମନ୍ତବ୍ୟ ଅନ୍ତର୍ଭୁକ୍ତ କରନ୍ତୁ।
2. ଟ୍ରାକିଂ ଇସ୍ୟୁକୁ ଉଲ୍ଲେଖ କରନ୍ତୁ (ଯଥା, `// #3498 — ପର୍ଯ୍ୟାୟ 2 ବୈଶିଷ୍ଟ୍ୟ, ଏପର୍ଯ୍ୟନ୍ତ କାର୍ଯ୍ୟକାରୀ କରାଯାଇନାହିଁ`)।
3. ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରୁଥିବା ସେହି PRରେ ଏଣ୍ଟ୍ରିଟି ହଟାନ୍ତୁ — ଆଉ କୌଣସି ସକ୍ରିୟ ଉଲ୍ଲଂଘନକୁ
   ଦମନ କରୁ ନଥିବା ଏକ ଅଚଳ ଏଣ୍ଟ୍ରି ନିଜେ ଏକ ତ୍ରୁଟି (କାର୍ଯ୍ୟକାରୀ ହେବା ପରେ 6A.3 ଅଚଳ-ପ୍ରବର୍ତ୍ତନ
   ଏକ ଅନାଥ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ପାଇଁ ଗେଟ୍କୁ ବିଫଳ କରିବ)।

ପରୀକ୍ଷାଗୁଡ଼ିକୁ ଶୀଘ୍ର ପାସ୍ କରାଇବା ପାଇଁ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ **ନାହିଁ**। ବଢ଼ୁଥିବା
ଅନୁମୋଦିତ-ତାଲିକା ସହିତ ଏକ ସବୁଜ ଗେଟ୍ ଗୁଣବତ୍ତାର ଏକ ମିଥ୍ୟା ଆଶ୍ୱାସନ।

### ଆପଣଙ୍କ PRରେ ଏକ ଗେଟ୍ ବିଫଳ ହେଲେ

1. **ଗେଟ୍ର ଆଉଟପୁଟ୍ ଯତ୍ନର ସହ ପଢ଼ନ୍ତୁ** — କେଉଁ ଫାଇଲ୍ କିମ୍ବା ସିମ୍ବଲ୍ ନିୟମଟି ଉଲ୍ଲଂଘନ କରିଛି, ଏହା ଆପଣଙ୍କୁ ଠିକ୍ ଭାବରେ କହିଥାଏ।
2. **ଉଲ୍ଲଂଘନଟି ସମାଧାନ କରନ୍ତୁ** — ଅଧିକାଂଶ ଗେଟ୍ ନିର୍ଦ୍ଧାରଣାତ୍ମକ ଫାଇଲ୍ସିଷ୍ଟମ୍ ଯାଞ୍ଚ, ଯାହା କୋଡ୍
   ସଠିକ୍ ହେବାମାତ୍ରେ ପାସ୍ ହୋଇଯାଏ।
3. **ଯଦି ଉଲ୍ଲଂଘନଟି ପୂର୍ବରୁ ଥିଲା** (ଅର୍ଥାତ୍, ଆପଣ ଏହାକୁ ସୃଷ୍ଟି କରିନାହାନ୍ତି, କିନ୍ତୁ ଗେଟ୍ ବର୍ତ୍ତମାନ
   ଏହାକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରୁଛି): ଯଥାର୍ଥତାର ମନ୍ତବ୍ୟ ଏବଂ ଏକ ଟ୍ରାକିଂ ଇସ୍ୟୁ ସହିତ ଏକ ଅନୁମୋଦିତ-ତାଲିକା ଏଣ୍ଟ୍ରି ଯୋଡ଼ନ୍ତୁ।
4. **ଯଦି ଗେଟ୍ଟି ଏକ ରାଚେଟ୍ ଅଟେ** (କଭରେଜ୍, ESLint ଚେତାବନୀ, ପୁନରାବୃତ୍ତି, ଜଟିଳତା):
   ଆପଣଙ୍କ ପରିବର୍ତ୍ତନ ମେଟ୍ରିକ୍କୁ ଆହୁରି ଖରାପ କରିଛି। ଅନ୍ତର୍ନିହିତ ସମସ୍ୟାଟି ସମାଧାନ କରନ୍ତୁ, କିମ୍ବା (କ୍ୱଚିତ୍) ପରିବର୍ତ୍ତନଟି ଉଦ୍ଦେଶ୍ୟମୂଳକ ଏବଂ ମେଟ୍ରିକ୍ର
   ଅବନତି ଗ୍ରହଣଯୋଗ୍ୟ ହେଲେ `npm run quality:ratchet -- --update` ଚଲାନ୍ତୁ — କିନ୍ତୁ PR ବିବରଣୀରେ ଏହାର କାରଣ ଲିପିବଦ୍ଧ କରନ୍ତୁ।
5. **ପରାମର୍ଶମୂଳକ ଗେଟ୍ଗୁଡ଼ିକ** (`continue-on-error: true`) କେବଳ ସୂଚନାମୂଳକ — ସେଗୁଡ଼ିକ ମର୍ଜ୍କୁ ଅବରୋଧ
   କରେନାହିଁ, କିନ୍ତୁ CI ସାରାଂଶରେ ଦେଖାଯାଏ। ତଥାପି ସେଗୁଡ଼ିକୁ ସମାଧାନ କରନ୍ତୁ।

## ଏକ ନୂତନ ଗେଟ୍ ଯୋଡ଼ିବା

1. `scripts/check/check-<name>.mjs` (କିମ୍ବା `.ts`) ସୃଷ୍ଟି କରନ୍ତୁ। ନୀତି ଗେଟ୍ଗୁଡ଼ିକ 0/1 ଏକ୍ସିଟ୍ କରନ୍ତି।
   ରାଚେଟ୍-ଶୈଳୀର ଗେଟ୍ଗୁଡ଼ିକ `collect-metrics.mjs` ମାଧ୍ୟମରେ `quality-metrics.json`କୁ ଏକ ମେଟ୍ରିକ୍ ନିର୍ଗତ କରନ୍ତି।
2. `package.json`ରେ `"check:<name>": "node scripts/check/check-<name>.mjs"` ଯୋଡ଼ନ୍ତୁ।
3. ଉପଯୁକ୍ତ ଜବ୍ର ଅଧୀନରେ `.github/workflows/ci.yml`ରେ ଏହାକୁ ସଂଯୋଗ କରନ୍ତୁ
   (ନୀତି → `lint` କିମ୍ବା `docs-sync-strict`; ରାଚେଟ୍ → `quality-gate`)।
4. ଯଦି ଏହାର ଏକ ଅନୁମୋଦିତ-ତାଲିକା ଅଛି, ତେବେ ଅଚଳ ଏଣ୍ଟ୍ରିଗୁଡ଼ିକ ସ୍ୱୟଂଚାଳିତ ଭାବେ ଚିହ୍ନଟ ହେବା ପାଇଁ
   `scripts/check/lib/allowlist.mjs`ରୁ `reportStaleEntries()` ପ୍ରୟୋଗ କରନ୍ତୁ।
5. ଗେଟ୍ର ଚିହ୍ନଟ ତର୍କକୁ ଅନ୍ତର୍ଭୁକ୍ତ କରି `tests/unit/build/`ରେ ଏକ ପରୀକ୍ଷା ଲେଖନ୍ତୁ।
6. ଏହି ଡକ୍ୟୁମେଣ୍ଟ୍କୁ ଅଦ୍ୟତନ କରନ୍ତୁ (ସମ୍ପର୍କିତ ଜବ୍ ଟେବୁଲ୍ରେ ଏକ ଧାଡ଼ି ଯୋଡ଼ନ୍ତୁ)।

### ମର୍ଜ / ଡିଡ୍ୟୁପ୍ (ଯାନ୍ତ୍ରିକ, କମ୍ ବିପଦ)

ପ୍ରତ୍ୟେକ ପ୍ରାର୍ଥୀକୁ 2026-06-17 ରେ ସକ୍ରିୟ ଗେଟ୍ ସ୍ଥିତି ସହିତ ଯାଞ୍ଚ କରାଯାଇଥିଲା (ବିଶ୍ୱାସ କରନ୍ତୁ, କିନ୍ତୁ ଯାଞ୍ଚ ମଧ୍ୟ କରନ୍ତୁ);
ଅନେକ "ସ୍ପଷ୍ଟ" ମର୍ଜ ଋଣ ଲୁଚାଇ ରଖିଥିବା ଜଣାପଡ଼ିଲା ଏବଂ ସେଗୁଡ଼ିକ **ସିଧାସଳଖ ପ୍ରତିସ୍ଥାପନଯୋଗ୍ୟ ନୁହେଁ**।
